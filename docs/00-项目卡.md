## 一、一句话目标

**让手机成为电脑 DSH 的第二块屏幕**：同一个会话两端都能操作、文件双向互通、AI 知道你在哪台设备。

## 二、"跑通"的可验证标准（阶段 1 的门禁）

一条证据链，缺一不算跑通：

1. 手机（4G，不在家）打开电脑的**官方界面**，看到的是电脑上同一个会话；
2. 手机发一句 → 电脑端同一会话里出现这句；
3. 电脑回复在手机上流式出现；
4. 证据留档：手机截图 ×1、电脑同会话截图 ×1、`/api/status` 日志 ×1。

> 阶段 2 才算"环境工程"：问 AI「我现在在哪、在用什么设备」它能答对（presence 注入）；AI 产出的文件能在手机上直接拿到。

## 三、路线（以 DSH 原生能力为主，不重写客户端）

| 代号 | 做什么 | 依据 | 工作量 |
|---|---|---|---|
| **R1（阶段 1）** | 把官方 Web GUI 安全地开到手机上：`webServer` + `connection.authenticatedUrl()` + Tailscale serve | 见"已确认事实" 1-3 | 0.5–1 天 |
| **R2** | presence 层：设备在线表 + `systemPrompt` 注入"你在哪" | `systemPrompt.section/context`；KDE Connect 的"能力位小包"思路 | 1–2 天 |
| **R3** | 文件层：官方 `attachments`/`workspaceFiles` + 自建 outbox 下载 + Taildrop 推送 | 官方文件服务已具备 | 1 天 |
| **R4（退路）** | 若 R1 手机上不能用 → 自建轻客户端，照抄 cc-remote 的 `asOfSeq` 冷历史 + `follow` 增量 | cc-remote `docs/dsh-integration.md`（MIT） | +3 天 |

**不做什么**：不做镜像会话（复制两份状态必然漂）、不做屏幕流/远程桌面、不做公网中继（Tailscale 已解决）。

## 四、已确认的技术事实（阶段 0 侦察结果）

1. **官方 GUI 只缺一个令牌，不缺域名白名单**：`http://127.0.0.1:62861/` 返回
   `401 dsh web authentication required; reopen the URL printed by dsh web`；
   换成 `Host: silence.tail9914d1.ts.net` 仍然是 **401 而不是 403** → 远程 authority 不是硬拒。
2. **有官方"发令牌地址"的接口**：`ctx.connection.authenticatedUrl(baseUrl)` ——"给普通 Web 应用地址加上本次进程的令牌"；配套 `authorizeIndex`（签发 cookie，TLS 时 `Secure`）、`allowsRemoteAuthorities`（`trustedHosts` 配了非 loopback 域名才为真）。
3. **Web 服务提供挂载点**：`ctx.webServer` 有 `getOrigin / register / registerUpgrade / tapIndex` —— 插件可以合法地加自有路由和 **WebSocket 升级**处理（反向代理不需要另开端口）。
4. **多端是框架内建概念**：宿主自带 `@deepseek-ai/dsh-api-remote-access`（非 owner Peer 的**按角色授权**、按资源过滤、每 Peer 访问快照）与 `dsh-api-remotes`，说明"给别人/给另一台设备看"是设计内的事，不是我们发明的。该包当前状态 `absent`（未装配）。
5. **审批/提问可以被接管**（waterfall 事件，已读契约）：
   - `approval/request` → `{agent, toolName, callId, reason, displayReason{en, zh…}, signal}` → 返回 `allowed-once | rejected | cancelled | unavailable`
   - `user-questions/request` → `questions[{id, question, detail, header, options[{label,description}], multiSelect}]` → 返回 `{answers:[{id, selected[], custom}]}`
   - 两个都要求"没人接管时 `next()` 回落"，否则会抢走电脑上的弹窗。

## 五、还没验证的（阶段 1 先验这 4 条，不写产品代码）

| # | 要验什么 | 怎么验 | 失败意味着 |
|---|---|---|---|
| V1 | 插件里能不能拿到 `authenticatedUrl()` 且能用 | 在插件里 `ctx.get('connection')` 取服务，打印一次地址（不回传明文 token 到日志） | 退回"从 dsh web 启动日志取 URL"的手工方案 |
| V2 | 手机 WebView/浏览器打开官方 GUI 可用吗 | 手机 4G 打开，发一条消息、看流式、点审批 | 走 R4 自建轻客户端 |
| V3 | WebSocket/SSE 能否穿过 tailscale serve | `tailscale serve --bg 62861` 后手机连上，看有没有实时更新 | 改挂 `webServer.registerUpgrade` 自建路径 |
| V4 | 令牌/cookie 在 https 下是否成立 | 打开后刷新一次页面，确认不掉登录 | 需要 trustedHosts 配置或自建登录跳转 |

## 六、风险与止损

| 风险 | 影响 | 对策 |
|---|---|---|
| 官方 GUI 在手机上不可用（桌面布局/键盘/触控） | R1 失败，+3 天走 R4 | 阶段 1 只验不建；两次验证失败立即转 R4 |
| **安全**：等于把整台电脑的 AI 控制权开到网上 | 最坏是被陌生人指挥你的电脑 | Tailscale ACL 限设备 + 单次令牌 + 可吊销 + 所有远程请求记审计日志；不做公网中继 |
| 两套入口并存（自制面板 + 官方界面） | 用户困惑、维护翻倍 | 只保留一个主入口，旧面板降级为"兜底/健康检查" |

**止损规则**：同一问题 3 次尝试或 10 分钟无进展 → 换路线；验证阶段禁止写产品代码；任何"看起来能用"都要留证据（截图/日志）才算。
