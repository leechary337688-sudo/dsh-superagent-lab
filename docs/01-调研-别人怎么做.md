# 别人怎么做的（调研摘要）

2026-11-08 · 阶段 0 侦察 · 来源：GitHub README/docs（`api.github.com` 读的公开仓库）· 每条都标了出处

## 一、结论先行

1. **没有人在做"镜像整机"。** 手机端项目全是"**会话级 API + 中继**"（happy / cc-remote / AgentFlow），VibeTunnel 做的是"终端流"，KDE Connect 是"设备能力插件"。镜像像素流在移动端根本不可用（带宽大、触控差、审批弹窗点不准）。
2. **信任模型分三档**：真端到端加密（happy）、自托管中继靠"数据在你自己机器上"（cc-remote）、宣称 E2E 但无可验证设计（AgentFlow，**未验证**）。
3. **对 DSH 最直接可抄的是 `muggle-stack/cc-remote` 的 `docs/dsh-integration.md`** —— 它已按 DSH 原生 `session/projections/page/follow` 接好，冷历史用 `asOfSeq` 游标、再 `follow` 增量，比"重放全部"稳。MIT，可抄代码。

## 二、五个项目对照

| 项目 | 形态 | 传输/信任 | 会话模型 | 对我们的价值 |
|---|---|---|---|---|
| [slopus/happy](https://github.com/slopus/happy) ★24.5k MIT Swift | 原生 App（自带 APNs/FCM） | 公网中继 + **真 E2E**（NaCl 密钥对、每会话 AES-256-GCM DEK；服务器只存密文） | 同一会话多端订阅；**单用户单调 seq**；`update`（持久）与 `ephemeral`（presence，不落库）分离；`localId` 去重；重连按 seq 补拉 | 协议设计的教科书；但"自建推送 + 双端 App"成本极高 |
| [muggle-stack/cc-remote](https://github.com/muggle-stack/cc-remote) ★25 MIT Python | Web + 自托管 Relay | Wrapper **主动出站**，不开入站端口；**无 E2E**（靠自托管担责） | 共享同一会话；`asOfSeq` 读冷历史 → `follow` 增量；事件答案要对上 `clientId+eventId` | **最该抄的 DSH 接法** |
| [714317168/AgentFlow](https://github.com/714307168/AgentFlow) ★16 MIT TS | Electron + 原生安卓 + Go Relay | 描述称 E2E，文档无可验证设计 | 每会话 `max syncSeq` → `after_seq` 增量；`content_md5` 判断裁剪；缺项按 id 单拉；出站串行 | 增量同步与"能力级授权"思路 |
| [amantus-ai/vibetunnel](https://github.com/amantus-ai/vibetunnel) ★4.7k MIT | 浏览器看终端 | 本机 server + Tailscale/ngrok；无内置 TLS，靠私网兜底 | WS + **整帧快照 `SNAPSHOT_VT`** 重同步 | "快照重连"这一招 |
| [KDE/kdeconnect-android](https://github.com/KDE/kdeconnect-android) ★1.5k **GPL-2.0** | 原生 | 局域网配对 | 设备状态**不是大对象**，而是每插件发小包：`connectivityreport`（网络）、`battery`、`ping`；文件是**推** | presence 的建模方式（只抄思路，代码不能抄进 MIT） |

## 三、11 条可抄清单

1. 中继只做**盲存储+转发**，内容客户端加密（happy `docs/encryption.md`）
2. 认证用**公钥 + 挑战签名**，不用密码；丢手机吊销公钥（happy `docs/api.md`）
3. 每会话一把 DEK、用公钥封装后存服务器（happy `docs/encryption.md`）
4. **单用户单调 seq** + `update`/`ephemeral` 分离（happy `docs/protocol.md`）→ 重连只拉 seq 之后，presence 不进库
5. 冷历史走 **`asOfSeq` 游标**，快照后再 `follow`（cc-remote `docs/dsh-integration.md`）
6. 断线用**整帧快照重同步**，不重放字节流（VibeTunnel `ARCHITECTURE.md`）
7. 审批/提问**整批原子关闭**、草稿按 device/session 隔离（cc-remote `docs/user-questions.md`）
8. 推送用"**证明正在看才不推**"，未知状态宁可多推（happy `focusTracker.ts`）
9. 设备状态拆成**能力位小包**（KDE `ConnectivityReportPlugin.kt`）
10. **能力级授权 + 过期撤销**（AgentFlow `controlled-remote-authorization.md`）
11. 设备侧**主动出站**连中继，永不开入站端口（cc-remote 架构）

## 四、三个"看起来对但会坑人"的做法

1. **公网中继"免费又简单"**：带宽/存储你出；不加密=明文（cc-remote 模式），加密了元数据仍泄漏（happy 自己列了 id/时间/设备/推送 token），且多设备密钥迁移复杂度陡增。
2. **PWA 当主力**：iOS 后台会掐 WebSocket、通知不可靠；要稳定推送就得原生 App（happy 为此自建推送 Worker）。
3. **镜像整机/像素流**：VibeTunnel 只做终端都要做快照；我们要做**会话级结构化事件**，不是屏幕流。

## 六、我们自己的额外发现（DSH 侧，别人不知道的）

1. 宿主已内置 `@deepseek-ai/dsh-api-remote-access`（非 owner Peer 按角色授权、按资源过滤、每 Peer 访问快照）与 `dsh-api-remotes` —— **"另一个设备/另一个用户看"是框架内建概念**，不是我们要发明的。
2. `ctx.connection.authenticatedUrl(baseUrl)` 能生成"带本次进程令牌的 Web 地址"；`ctx.webServer` 提供 `register / registerUpgrade`（反向代理可合法挂载）。
3. 官方 GUI 现在返回 `401 dsh web authentication required; reopen the URL printed by dsh web`；带 `Host: <ts.net 域名>` 仍是 401（不是 403）→ **只缺令牌，域名不被硬拒**。
4. 审批/提问可被插件接管：`approval/request`、`user-questions/request`（waterfall，含中文 `displayReason` 与完整选项）。

> 这些意味着：**我们可能不用自己造桥**，只需要"把官方客户端安全地送到手机上 + 补 presence 与文件这两层"。这也是本项目和 phone-bridge 的本质区别。
