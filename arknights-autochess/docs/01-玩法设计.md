# 01 · 玩法设计

本文只定**骨架与规则类别**，不填具体数值和角色。数值属于内容（`content/config/balance.json` 与
`content/operators/*.json`），等设计确定后再做。

## 1. 三条设计支柱

1. **运营决策**：钱怎么花、什么时候升本、留牌还是刷新、阵容走大盟约还是拼小盟约——和自走棋一样，
   每回合都在资源约束下做选择；
2. **塔防地形**：不是两个阵容自动对撞，而是**敌人沿路线进攻、干员靠格子和朝向拦截**。位置、朝向、
   攻击范围、阻挡数、地形和波次都影响结果（这是「方舟味」的核心）；
3. **低压力合作**（远期）：多人是**合作**而不是淘汰；各自发育、可帮队友补漏，输赢共同承担。

## 2. 核心循环

```
                ┌──────────────────────────── 一局 14 回合 ────────────────────────────┐
                │                                                                     │
  ┌─────────────┴─────────────┐      ┌──────────────────┐      ┌───────────────────┐   │
  │ 休整期 PREP               │      │ 作战期 COMBAT    │      │ 结算期 SETTLE      │   │
  │ · 商店招募/刷新/冻结      │ ───▶ │ · 敌人按波次入场 │ ───▶ │ · 漏怪扣目标生命   │   │
  │ · 三合一升星             │      │ · 干员自动攻击   │      │ · 发金币（基础+    │   │
  │ · 升级调度中心           │      │ · 阻挡/技能释放  │      │   利息+连胜连败）   │   │
  │ · 摆放/朝向/配装         │      │ · 目标生命归零→结束│     │ · 回合 +1，回休整期 │   │
  │ · 盟约/装备/决策 3 选 1  │      └──────────────────┘      └───────────────────┘   │
  └───────────────────────────┘                                                      │
                                                                                    ▼
                                                                              第 14 回合后结算
```

对应代码：`src/sim/state.ts` 的 `Phase`（`prep` / `combat` / `settle` / `finished`），
`src/sim/run.ts` 的 `advancePhase()`。M0 里作战期由**占位解算器**瞬时完成（完美防守），
所以 UI 上看到的是 `prep → settle → prep`。

## 3. 运营系统（自走棋部分）

| 系统 | 规则骨架 | 数据/代码位置 |
|---|---|---|
| **商店** | 5 格；按调度中心等级抽稀有度；手动刷新 2 金；冻结商店可保留到下一回合 | `sim/shop.ts` + `config.balance.shop` |
| **调度中心（等级）** | 1–9 级；逐级涨价；等级影响商店稀有度与上阵人数 | `sim/economy.ts` + `config.balance.leveling` |
| **经济** | 每回合：基础收入 + 利息（每 10 金 1 金，上限 5）+ 连胜/连败补贴 | `sim/economy.ts` |
| **三合一** | 同名同星级 3 个 → 升 1 星（1→2→3 星）；立即合成 | `sim/merge.ts` |
| **整备区/上阵位** | 整备区 9 格；上阵人数按等级上限；只能放在可部署格 | `sim/board.ts` + `sim/run.ts` |
| **装备** | 基础装备 + 合成装备（同 TFT）；配发后锁在干员身上 | 数据 schema 已留 `items`，逻辑 M2 |
| **局内决策** | 特定回合后 3 选 1：① 悬赏（多刷怪换钱）② 道具补给（装备）③ 战术（改规则/削弱敌人） | M3；参考卫戍协议的三种决策类型 |

经济数值是**占位默认值**（开局 10 金、每回合 5 金、利息上限 5），标记为「待平衡」，不是最终设计。

## 4. 战斗系统（方舟塔防部分）

这一块决定「像不像方舟」，也是 M1 的主要工作量。

| 规则 | 说明 | M1 是否必须 |
|---|---|---|
| **部署格** | 只有地图上标记为 `deployable` 的格子能站人；地图底部三行是主要部署区（用户提到的「底部格子」） | ✅ |
| **朝向** | 部署时选择上/下/左/右；远程干员只打面朝方向一侧（方舟规则，范围形状按朝向旋转） | ✅（简化：矩形/直线） |
| **攻击范围** | 近战 1 格；远程按「前方 N 格 + 两侧」的简化形状；高台（`highGround`）可放远程 | ✅（简化） |
| **阻挡** | 近战阻挡数 > 0 的敌人会被拦住；阻挡者倒下后由相邻/接触的干员接替 | ✅ |
| **技能** | 方舟技能是「自动回复/自动释放」：按策略在满足条件时放技能 | ⏳ M2 |
| **敌人** | 沿路线从 `spawn` 走向 `goal`；有血量/攻击/速度/是否飞行 | ✅（直线寻路即可） |
| **波次** | 每回合按 `waves` 数据出怪：种类、数量、间隔、入口 | ✅ |
| **漏怪** | 敌人走到目标格 → 扣目标生命；生命归零整局结束 | ✅ |
| **地形装置** | 阻隔工事、射击台、吹风机、沼泽……（卫戍协议有大量此类装置） | ⏳ M3 |

M1 的战斗目标是**可验证的最小闭环**：1 张地图、1 个敌人、1 个近战干员、1 条路、能扣血。
先不做：技能、元素、召唤物、多波次混合、异常状态。

## 5. 盟约（对应羁绊）

- 盟约由「势力/阵营」+「职业/标签」构成，例如「深海猎人 ×3/×5」「术师 ×2/×4」；
- 在场干员按 `synergyIds` 归档，达到 `thresholds` 的第一/第二层阈值就激活对应效果；
- **层数**（卫戍协议的「叠层」）是可选扩展：把战力成长转成可读指标，避免玩家迷失；M2 再考虑；
- 与云顶的区别：命名用方舟的势力/职业体系；效果偏向「方舟式」数值（攻防/技力/阻挡），而不是纯伤害乘区。

数据结构见 `src/content/schema.ts` 的 `SynergyDef`；当前 `content/synergies/` 为空。

## 6. 回合与节奏（占位参数）

- 一局 **14 回合**（`config.round.total`）；
- 休整期 **40 秒**（单机；联机参考卫戍协议会缩短，M5 再说）；
- 难度分层：标准 / 险境 / 绝境（官方三档），对应敌人强度与决策点数量；M3；
- 最终回合之后可选「最终领袖轮」（共享血条、超时扣血），M4。

## 7. 多人合作（远期，架构已预留）

参考卫戍协议的「同盟模拟」：

- 1–4 人**合作**，各自独立生命、独立经济，共享卡池（或部分共享）；
- **联防**：有人漏怪时，完美防守的队友带着阵容帮忙拦截；
- 局内交流：表情/快捷消息；
- 技术方案见 [02-技术架构](02-技术架构.md) 的「联机预留」；M5 才做，不阻塞单机。

## 8. 我们这版的取舍（与参考的差异）

| 取舍 | 说明 |
|---|---|
| 单机优先 | 先把一局单机做完整，再谈联机；联机只预留接口 |
| 不做 PvP | 云顶是八人淘汰赛；我们做合作/单机，避免匹配与平衡复杂度 |
| 不做抽卡养成 | 干员直接用商店招募，不做账号、等级、潜能 |
| 简化技能 | 先做「自动攻击 + 一个被动/主动」，不做 283 个技能 |
| 数值自研 | 参考官方数据理解结构，但不照搬数值；避免版权问题，也便于平衡 |

## 9. 待定问题（等设计/你拍板）

1. 攻击范围形状：矩形、十字还是方舟原版的「朝向 + 偏移格」？M1 先矩形，后面再改。
2. 阻挡与接替规则：严格按方舟「阻挡者倒下→接触者接替」，还是简化为固定阻挡位？
3. 技能复杂度：每个干员 1 个技能够不够？
4. 联机是否第一版就要？
5. 是否使用官方干员名/数据（非商业本机）还是原创角色（可公开发布）。

这些问题不阻塞框架，但会决定 M1–M3 的内容量。
