# 06 · 开发路线图与验收

本文按「先跑通、再加内容」排里程碑。每个里程碑都有**可验证的验收标准**，完成后再进入下一个。

## 里程碑总览

| 阶段 | 目标 | 关键交付 | 验收 |
|---|---|---|---|
| **M0 框架** | 目录/架构/数据格式/可运行空壳 | 当前仓库 | `npm run check` 全绿 + 页面截图 |
| **M1 战斗原型** | 一局能打 | 1 张正式地图、3 个占位干员、1 种敌人、1 套波次、tick 战斗循环、扣目标生命 | 手动打完 3 回合，漏怪扣血、干员会攻击；`npm run check` |
| **M2 运营闭环** | 自走棋部分完整 | 商店/经济/升本/三合一/整备区/盟约层数/摆放交互 | 一局 14 回合能靠运营变强；盟约激活有反馈 |
| **M3 完整一局** | 有难度、有结算 | 3 档难度、决策 3 选 1、装备、结算界面 | 能从头玩到尾并看到结算；难度差异可感知 |
| **M4 内容与表现** | 像个游戏 | 美术/音效/动画/特效、10+ 干员、5+ 盟约、3+ 地图、性能优化 | 60 FPS；内容可玩性通过人工验收 |
| **M5 联机（可选）** | 1–4 人合作 | 房间/协议/服务端校验/联防 | 2 人局域网联机完成一局 |

## M1 · 战斗原型（下一个里程碑）

**目标**：一局里「摆干员 → 敌人从入口走到目标 → 干员攻击 → 漏怪扣血」能真实发生。

**任务**

1. `sim/battle/` 拆出子目录：`tick.ts`（固定 30Hz 循环）、`enemy.ts`（移动/到达目标）、
   `attack.ts`（攻击间隔/伤害）、`targeting.ts`（朝向 + 范围形状）、`block.ts`（阻挡与接替）；
2. 寻路：先做**单条预设路径**（地图 `layout` 派生），不做 A*；
3. `BattleSpec` 扩展：把地图、干员站位/朝向、波次、种子带进去；返回 `BattleReport` + 事件流（给渲染用）；
4. 渲染：敌人移动、血条、攻击线、伤害数字（Pixi）；
5. 摆放交互：点击整备区 → 点击部署格 → 选朝向；拖拽可后置；
6. 内容：1 张正式地图、3 个占位干员（近战/远程/重装）、1–2 种敌人、1 套 3 回合波次；
7. 测试：战斗确定性（同 spec 同结果）、阻挡/伤害/漏怪单测、golden 战斗报告。

**验收**

- 手动走完 3 回合：有敌人进场、被阻挡、被击杀、漏怪扣目标生命；
- 同一份 BattleSpec 跑两次结果完全一致（测试）；
- `npm run check` 全绿；
- 记录一次战斗的 tick 数与结果到文档/PR。

**不做**：技能（除普攻）、元素、召唤物、飞行、地形装置、多人。

## M2 · 运营闭环

**目标**：不用战斗也能感觉到「运营在变强」。

**任务**

- 商店卡池（有限张数、共享/私有、刷新概率按等级）；
- 三合一动画/提示、卖牌、锁定；
- 盟约层数计算 + 面板高亮；
- 星级属性成长、上阵人数与等级联动；
- 摆放/移动/撤回、朝向轮盘；
- 经济曲线调参，跑一局 14 回合验证不会「前 5 回合就崩」。

**验收**：完整跑 14 回合（战斗可用 M1 占位或真实解算），能截图展示不同阵容/盟约。

**不做**：装备、决策卡、难度、结算。

## M3 · 完整一局

**任务**：3 档难度（标准/险境/绝境）、第 N 回合后的 3 选 1 决策（悬赏/装备/战术）、
装备与合成、最终回合结算/称号、存档（localStorage）与继续游戏。

**验收**：从开局到结算完整跑通；3 档难度敌人数值不同；决策对局势有可感知影响。

## M4 · 内容与表现

**任务**：10+ 干员、5+ 盟约、3+ 地图、波次表、UI 视觉打磨、音效/BGM、技能特效、
性能（对象池/图集/按需加载）、移动端横屏适配。

**验收**：60 FPS；人工试玩认为「像个游戏」；素材许可清单通过（见 05 文档第 6 节）。

## M5 · 联机（可选）

**前提**：M1–M4 稳定，且明确要做 1–4 人合作。

**任务**：Node 服务端（`ws`）、房间/座位、协议校验、公开/私有状态拆分、
客户端战斗模拟 + 服务端校验（参考项目的做法）、断线重连、联防。

**验收**：2 人局域网完成一局；服务端能拒绝非法 intent；断线 1 分钟内能回来。

## 建议的下次开工顺序（人回来之后）

1. 看 [00-总览](00-总览与范围.md) 末尾「回来先决定的 4 件事」，拍板素材路线与战斗深度；
2. 打开 `npm run dev` 点一遍现有空壳，确认布局/信息架构是否符合预期；
3. 填第一批内容（3 个干员 + 1 套波次），跑 `npm test` 确认校验器工作；
4. 按 M1 任务清单从 `sim/battle` 的 tick 循环 + 寻路开始写（不要先做美术）；
5. 每完成一小步跑 `npm run check`，保持主干可运行。

## 每阶段的 Definition of Done

- [ ] 功能按验收标准手动验证过（有截图/录屏或测试证据）
- [ ] `npm run check` 全绿
- [ ] 新增/修改了数据格式 → 同步更新 `docs/04` 与测试夹具
- [ ] 新增模块/依赖 → 更新 `tools/check-layers.mjs` 与 `docs/02`/`03`
- [ ] 素材/依赖许可记录到 `NOTICE.md` 或 `docs/05`
- [ ] PR 描述写清「用户可见变化」与验证方式

## 风险与止损（复用 00 文档）

- 同一问题 3 次尝试无进展 → 停下换方案，记录到 PR/文档；
- M1 若 2 周没有可玩闭环 → 砍到「1 干员 + 1 敌人 + 1 条路」，先验证「好不好玩」；
- 内容生产（角色/美术）是长期成本：M4 前不追求数量，先把 3 个角色做到「手感对」。

## 需要人拍板的事（不阻塞框架，但阻塞 M2+）

1. 素材路线（自制 / CC0 / 本机官方素材非商业）；
2. 战斗深度（完整方舟规则 vs 简化）；
3. 是否第一版就做联机；
4. 角色与数值用官方还是原创；
5. 目标平台（桌面浏览器优先？移动横屏？）。
