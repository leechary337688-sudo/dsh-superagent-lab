# 02 · 技术架构

## 1. 选型：为什么是浏览器 + TypeScript

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **Web：TypeScript + Vite + PixiJS + Preact** | 即开即玩、迭代快、无编辑器依赖、sim 可在 Node 跑测试、跨平台、参考项目验证过 | 3D/重度特效弱于 Unity；需要自己搭 UI 框架 | ✅ **采用** |
| Unity（C#/URP） | 编辑器、Spine/3D、音频生态成熟；商业化手游标准 | 初次成本高、Agent 迭代慢、需要安装 Editor、仓库体积大 | 备选；架构上把 sim 设计成引擎无关，但 C# 不能直接复用 TS |
| Godot 4 | 开源、轻量、2D 强 | 团队/生态小、需要桌面端 | 备选 |
| Phaser 3 | 游戏框架完整（场景/输入/音频/Tween） | 自定义 UI 和复杂逻辑不如「Pixi + DOM UI」灵活 | 不采用 |

**结论**：`Vite` 负责开发服务器与构建，`PixiJS` 只画棋盘/单位/特效（WebGL/WebGPU），
`Preact` 负责 HUD/商店/面板等 DOM 界面。两者通过 `GameSession` 的单向数据流连接。

> 为什么不用 Unity：这个项目的第一目标是「把玩法跑通并持续迭代」，Web 的反馈循环最短；
> 如果将来要做 3D 棋盘/大量特效，PixiJS 也能接 three.js（参考项目就这么做），或者把 sim 搬到服务端后换前端引擎。

## 2. 分层与依赖方向

```
┌──────────────────────────── 表现层（浏览器） ────────────────────────────┐
│  ui/ (Preact + DOM)          render/ (PixiJS 棋盘)                       │
│  HUD / 商店 / 整备区 / 盟约   格子 / 部署标记 / 单位 / 特效（M1+）          │
└───────────────┬───────────────────────────────┬─────────────────────────┘
                │ 调用意图（buy/refresh/levelUp/advance）                 │ 只读状态快照
                ▼                               ▼
        ┌──────────────────────────────────────────────┐
        │ app/session.ts  GameSession                  │
        │ 唯一的「写入口」：意图 → sim action → 新状态  │
        └───────────────────┬──────────────────────────┘
                            ▼
        ┌──────────────────────────────────────────────┐
        │ sim/  确定性模拟（纯 TS，无 DOM/渲染依赖）     │
        │ economy / shop / merge / board / run / battle │
        └───────┬──────────────────────────┬───────────┘
                ▼                          ▼
        ┌───────────────┐          ┌────────────────────┐
        │ core/         │          │ content/           │
        │ 网格/随机/数学 │          │ 加载 + 校验 JSON    │
        └───────────────┘          └─────────┬──────────┘
                                             ▼
                                   content/*.json（数据即内容）
```

硬规则（由 `tools/check-layers.mjs` 自动检查）：

- `core/` 不依赖任何其他模块，也不依赖第三方包；
- `content/` 只依赖 `core/` 的类型，以及 `content/` 下的 JSON；
- `sim/` 只依赖 `core/` 和 `content/` 的**类型**，禁止 DOM/渲染/UI/第三方包；
- `render/`、`ui/`、`app/` 只能依赖下层；不允许 `sim/` 反向 import 它们；
- `sim/` 里禁止 `Math.random`、`Date.now`、`new Date`、`performance.now`、浏览器 API 和
  `Math.sin/cos/pow/hypot` 等平台实现可能有末位差异的函数。

## 3. 单向数据流

```
用户点击 → UI 调 session.buyShopSlot(i)
        → sim action 返回 ActionResult { ok, state, message }
        → session 若 ok 则替换状态并通知订阅者
        → Preact 重渲染 + Pixi renderer.render(newState, map)
```

- 状态是不可变快照（每个 action 返回新对象），UI 只读；
- 失败的 action 返回原状态引用，UI 只显示 message，不处理异常；
- 渲染层**不参与判定**：它拿到什么状态就画什么，避免「画面和逻辑不一致」。

## 4. 确定性模拟（为回放、测试、联机做准备）

| 措施 | 实现 |
|---|---|
| 种子随机 | `core/rng.ts` 的 mulberry32；状态里的 `rngState` 是可序列化的 number |
| 固定 tick | 战斗用整数 tick 计时（计划 30 tick = 1 秒）；M0 只有报告字段，M1 接 tick 循环 |
| 禁止墙钟/真随机 | `tools/check-layers.mjs` 扫描 `sim/`，违规即失败 |
| 禁止平台相关数学 | 只用四则运算与 `Math.sqrt`；其余走 `core/math.ts` 或简化算法 |
| 无隐藏状态 | 一局全部状态都在 `RunState` 里，可 JSON 序列化；实例 uid 可预测（`u1`、`u2`…） |
| 可测试 | Vitest 直接对纯函数断言；关键流程（M1 起）加 golden 测试 |

> 为什么值得从第一天就这么做：一旦模拟不确定，「联机校验、断线重连、回放、平衡测试」都要返工。
> 参考复刻项目（Stronghold-Protocol）正是靠「固定 1/30 秒 tick + 种子 PRNG + 禁用 Math.sin/cos/pow」
> 做到浏览器和 Node 结果一致——我们只借鉴这个工程结论，不复制其代码。

## 5. 渲染与 UI 的分工

| 层 | 技术 | 负责 | 不负责 |
|---|---|---|---|
| 棋盘 | PixiJS | 格子、部署标记、单位、敌人、攻击范围、特效、镜头缩放 | 按钮、数值面板、文字排版 |
| 界面 | Preact + DOM/CSS | HUD、商店、整备区、盟约、提示、设置 | 棋盘逻辑 |
| 资源 | `public/assets/` + asset registry（M1） | 立绘/小人/图标/音效/字体 | 游戏规则 |

为什么分开：DOM 做 UI 的排版/可访问性/输入法/中日文字体都比 Canvas 内画 UI 省事；Pixi 只做「画面」。

## 6. 数据驱动

- 所有内容都是 `content/` 下的 JSON：规则参数（`config/`）、干员、技能、盟约、装备、敌人、波次、地图；
- `src/content/loader.ts` 用 Vite `import.meta.glob` 在构建时收集 JSON——**新增文件不用改代码**；
- `src/content/validate.ts` 在启动/测试时校验：id 唯一、引用完整、地图行宽、数值合法；
- 类型定义 `src/content/schema.ts` 是唯一事实来源；数据字段说明见 [04-数据模型](04-数据模型与Schema.md)；
- 地图用 ASCII + legend，改地形比改坐标数组直观；渲染层不直接读 JSON，只读解析后的 `GridMap`。

## 7. 联机预留（M5，不在当前范围）

单机版本已经按「动作 + 状态」组织，联机时可以：

1. **服务端权威**：服务端持有 `RunState`，校验每个 intent（买/刷新/升级/推进），广播公开状态；
2. **客户端战斗模拟 + 服务端校验**（参考项目的做法）：战斗在各自浏览器里用同一份 spec 跑，服务端校验结果区间；
3. **协议**：JSON 消息，`{t: 类型, ...}`；首版只需要 `hello`、`g.*`（局内意图）、`m.*`（状态/广播）、`b.*`（战斗 spec/结果）；
4. **状态同步**：`RunState` 已可序列化，公开状态/私有状态拆分（商店和金币是私有，棋盘/盟约是公开）。

M5 之前不引入 WebSocket、账号、房间服务；`net/` 目录先不建，等协议定了再加（加之前在 `check-layers` 登记）。

## 8. 测试策略

| 层级 | 工具 | 测什么 |
|---|---|---|
| 单元测试 | Vitest | rng/grid/经济/商店/三合一/摆放/回合状态机/内容校验 |
| 内容校验 | Vitest + `validate.ts` | 真实 `content/` 目录合法；坏数据能报出具体问题 |
| 架构守卫 | `tools/check-layers.mjs` | 模块边界、`sim/` 确定性约束 |
| 构建验证 | `vite build` | 生产构建能过 |
| 手工/截图 | 浏览器 | UI 骨架、状态流、后续的棋盘表现 |
| 后续（M1+） | Playwright / golden | 端到端一局、确定性回归 |

`npm run check` = `check:layers` + `typecheck` + `test` + `build`，CI（`.github/workflows/game-ci.yml`）跑同一条命令。

## 9. 性能与资源（M1 目标）

- 60 FPS（桌面浏览器），单位 ≤ 50、敌人 ≤ 100；
- 棋盘每次状态变化重画 Graphics（当前规模足够）；单位/特效多了改对象池 + 脏标记；
- 图片用 WebP/PNG 图集；音频用 OGG/MP3；字体子集化（中文字体体积大，见 05）；
- 首屏 < 2 MB（不含素材），素材按需加载。

## 10. 构建与部署

- `npm run dev`：Vite 开发服务器（5173）；
- `npm run build`：`vite build` 产出 `dist/`（`base: './'`，可放任意子路径静态托管）；
- `npm run preview`：本地预览产物；
- 部署目标：任意静态托管（GitHub Pages / Netlify / 自有服务器）；联机版以后再加 WebSocket 服务。

## 11. 关键决策记录（ADR）

| # | 决策 | 理由 | 可回退性 |
|---|---|---|---|
| 1 | Web（TS + Vite）而不是 Unity | 迭代反馈快、Agent/人类都好改、跨平台即开 | 中（sim 可重写为 C#，但 UI 要重做） |
| 2 | PixiJS + Preact 分工 | Pixi 画面、DOM 做界面，各用所长 | 高（render 只依赖状态快照） |
| 3 | 确定性 sim + 数据驱动 | 回放/单测/联机都靠它 | 低（越早越好，一旦内容多了很难补） |
| 4 | 单包分层，不拆 monorepo | 降低工具与依赖复杂度 | 高（联机时拆 `packages/sim`） |
| 5 | ASCII 地图 + legend | 改地形直观、review 容易 | 高（可换 JSON 坐标） |
| 6 | 战斗用接口占位（BattleSimulator） | M0 不阻塞 UI/回合流程，M1 平滑替换 | 高 |
